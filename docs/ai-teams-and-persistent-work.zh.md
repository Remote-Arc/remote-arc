# 持久任务、AI 员工与 Team：产品和执行设计

状态：Beta 发布候选；生产部署和验收范围单独记录。更新于 2026 年 10 月 20 日。

## 开发分支已实现与仍待完成的范围

已实现：账户归属及版本化员工/团队配置、独立 AI 团队页面、单聊、团队会话、临时群聊、可搜索的会话与员工列表、@ 指定员工徽章、自动分派和全员选择。切换房间会保留当前页面内的未发送草稿及失败重试身份。创建资料和群聊不会调用模型，也不要求 Task、截止时间或预算表单。

持久队列保存真实消息、发送时的员工身份和接收人、同事交接、工具实际返回及可分页历史。自动分派先唤醒协调人或一位成员，需要时再找同事；同一房间当前串行执行，并服从账户并发限制。空闲房间不调用模型。

后台调度属于基础设施：当前推理轮提出目标员工或团队，服务端校验真实用户目标、配置版本、稳定派发身份以及继承和当前权限交集。没有持续推理的调度员工，也没有额外的调度模型调用。跨团队交接必须预先允许；子会话的实际回复、失败和未知状态一次性回传原会话，附完整记录链接，不能据此宣称根目标已验收。

Arc Chat 已支持准备员工资料草稿：名字、职责、模型与头像均可编辑，资源权限由用户在确认前选择。点击“创建员工”后原子保存，重复确认不会重复创建，也不会调用模型或自动开工。草稿刷新后仍保留，可取消、七天后过期，创建后可直接进入员工单聊。

仍待完成：聊天创建可编辑的团队确认草稿、跨运行持久目标续跑、根目标验收、完整记录/用量筛选与导出。可选根任务上限尚未绑定到每次房间执行，现有账户 Credits 已统一计量。生产迁移、真实模型验收和受保护发布仍待完成。详见 [AI 团队功能地图](feature-map/ai-teams.md)。

## 产品对象

| 对象 | 用户定义什么 | 生命周期 |
| --- | --- | --- |
| AI 员工 | 名字、头像、模型、职责、工作说明、技能和可使用的能力 | 长期保存；没有待办不调用模型 |
| Team | 名字、目标领域、成员、协调者及交接规则 | 长期保存；成员变更不能扩大已有任务的授权 |
| Task / Outcome | 要交付的结果、负责人或 Team、验收条件、账户和资源范围 | 从创建到验收、取消或终止 |
| 持久任务方式 | 可选截止时间和额外总上限、续跑和停止条件 | 同一个 Task 下多次有界运行，累计消耗同一预算 |
| Run | 某名员工在某个阶段的一次模型与工具执行 | 有界、可取消、可追踪，不等同于整个目标完成 |

AI 员工、Team 与持久任务是独立维度。一个员工可以接普通任务或持久任务；一个 Team 也可以共同完成两类任务。定时例行任务是另一个维度：每天开始一次工作，不等于昨晚未完成的工作无限续跑。

## 入口和用户流程

AI 团队必须有独立的完整功能页面，Tasks 提供入口与关联目标。独立页面包含员工和团队管理、员工单聊、团队群聊、工作进展以及活动记录。Tasks 管理任务目标、负责人、分工、进度、预算、等待原因和最终回执，通过稳定 ID 引用员工、团队和会话。团队协作不要求隔夜，也不要求先创建 Task；正常问答和讨论应当直接可用。

Arc Chat 同样支持创建和管理，例如“建一个产品团队，Alice 负责设计，Bob 负责开发”。聊天先生成可编辑草稿，展示名字、头像、职责、模型、成员与权限；用户确认后才真正保存。聊天明确返回对象链接，刷新后仍可在管理页面找到。模型不能仅用一句“已创建”代替实际写入。

聊天识别到“隔夜、到明早、我离开后继续”等需求时，推荐持久任务卡片。默认按现有套餐和账户 Credits 工作，用户无需先填预算表。推荐卡片展示目标、负责人/Team 和必要的权限信息，可直接创建；截止时间和额外 Credits 总上限放在可选高级设置。额度用完后暂停并提示升级或充值。推荐本身不开始托管，也不扣除执行费用。

草稿和确认分开：模型可准备草稿，确认只能来自经过身份、CSRF、版本校验的用户操作。确认使用幂等键，重复点击返回同一对象；改变草稿内容需要重新确认。单纯保存员工或团队不触发工作。

## 员工和团队配置

员工保存模型 ID，并在执行时重新检查当前账户可用模型、方案和额度。模型下线、权限变化或预算不足时显示具体阻碍。替换为其他模型、启用付费备选模型或扩大消费上限，需要用户预先选择或再次确认。

头像支持系统头像和用户上传；上传应限制大小、类型，重新编码并通过受控存储提供，不直接把任意外部链接作为页面图片来源。头像生成如产生模型费用，应独立展示费用并计入明确预算。

职责与技能是工作说明，不能授予权限。有效执行权限取任务授权、员工配置、当前账户连接权限和设备本地策略的交集。Team 不拥有隐含的“管理员通行证”；成员也不能继承创建者未授予任务的私人账户权限。第一版明确按账户/现有工作空间归属隔离，跨用户组织共享需另行建立成员授权规则。

团队围绕一个 Outcome 工作，显式分派带输入、输出、依赖与验收的子工作。协调、开发、设计、财务角色可以使用不同模型。交接传递已授权的必要资料、产物标识、待办和证据；不向所有成员广播无关私人数据。成员之间的消息属于工作数据，不能自行变成新授权。

## 员工单聊、团队群聊与跨团队协作

员工有持续的身份、职责、配置和受权限约束的记忆。用户可以直接单聊，也可以进入团队群里提问、讨论和分派工作；适合回应的成员及时回答。不同团队可以在授权范围内互相发送消息和交接工作。员工之间的协作消息必须是真实保存、可查看的会话消息，不能只显示一个不可核查的“团队讨论中”。

会话是独立对象，至少区分用户与员工单聊、团队群聊和明确授权的跨团队会话。每条消息保存真实作者 ID、接收方/会话、时间、关联任务、回复和交接关系；作者由服务端确定，模型不能冒充用户或其他员工。一个会话可关联多个任务，一个任务也可关联多个会话；普通聊天不自动创建任务。

消息投递与模型唤醒按事件处理，按接收方和消息 ID 去重。@ 提及、直接提问、明确指派和必要交接决定谁需要回应，避免所有员工对每条消息无限相互回复。员工可以并行处理不同工作；同一会话的用户新消息能够被及时纳入，长任务不应占满全部交互容量。协调和成员之间的模型调用同样记录并计费，后台讨论受明确预算约束。

用户不必给员工或团队设定工作时限。目标任务可以没有截止时间，直到验收通过或出现需要用户解决的阻碍；每个技术执行片段仍保持有界并从检查点续接。员工身份、会话生命周期、一次聊天回复和一个目标的完成状态互相区分，不能因片段用完而宣告目标完成。

## 全程可见与独立页面

独立 AI 团队页面至少包含：员工目录与配置、Team 目录与成员、会话列表与群聊、关联目标和任务、可筛选的活动时间线。可以从 Tasks 跳入某个 Team、会话或员工，也能在 AI 团队页面直接查看和创建工作。

所有实际发生的用户单聊、员工间消息、团队讨论、跨团队交接、任务分派、工具调用、权限确认、预算预留与结算、检查和状态变化都形成持久记录。按员工、团队、任务、会话、时间和事件类别查询，并可从回执跳回原始事件。消息编辑/撤回、成员变更和配置版本也留下事件，不能静默改写历史。界面应显示事件内容与真实结果，不只显示事件计数。

这套记录覆盖实际通信和执行证据；不采集或展示密钥、完整凭证与模型的私有内部推理。记录中必要的敏感信息应按用户权限呈现或脱敏，不把外部内容当作授权。用户应明确知道保存范围、保留期、删除/导出方式；跨账户或组织的记录不能越权查询。

服务端存储是事实来源，聊天、任务和活动页引用同一消息/事件 ID。分页不丢失已有历史，断线重连能补齐事件；事件通知只是唤醒信号，重新拉取持久记录后才能展示。员工发起了真实操作却没有可追溯记录，应当视为验收失败。

## 共用运行底层

沿用现有 Cloudflare Worker / Durable Object、automations 注册表、调度租约、模型费用账本、Apps 派发和本地设备权限层。已有 planned-goal-runtime.ts 的阶段、检查点、隔离工作区和验证规则可复用。当前 arc-work.ts 的原生任务每次仅创建一次有界 chat run；跨多次运行直到目标完成还需要实现，不能把现状称作完整隔夜托管。

同一个 Task ID 贯穿入口、员工、子工作、模型请求、工具调用、产物和验收。Arc 与 Connect 共用任务记录和状态，但控制器明确归属：Arc 可主动启动下一次受预算限制的推理；Connect 的普通 MCP 连接不能唤醒任意第三方聊天。控制器移交需要明确授权和版本校验。

每个阶段保存已执行动作、真实资源 ID、当前进展、下一步、未决效果与验收结果。下一轮从持久化检查点恢复；压缩聊天上下文不能删除用于判定完成和避免重放的持久记录。重启、部署、断线后先核对已发生的效果，再执行后续动作。

调度按至少一次投递设计，使用租约、版本和派发记录防止两个 worker 同时推进同一阶段。第三方写入沿用稳定幂等身份；效果不明时进入待核对状态，不能换一个员工重新提交同一付款、订单或 Issue。

## 共享预算和停止条件

默认直接按套餐使用账户 Credits，用户不必为任务或每名员工单独设置预算。员工、协调、验收、失败尝试和续跑都从同一真实账户额度结算，不能为成员复制额度。仅在用户主动启用高级设置时，根 Task 增加一个额外的 Credits 总上限；子工作上限只能更小。账户额度、运行上限和平台运营资金限制继续执行。

每次模型调用先在同一账本中原子预留；并发员工不能各自读取余额后分别花完总预算。返回用量后结算，费用不明的预留继续占用。子工作取消不等于未知费用自动归零。账户 Credits 耗尽或触及用户主动设置的额外上限后，停止新的计费调用，保留已有结果，提示升级、充值或调整自选上限。用户补充有效额度后，可以从检查点继续。

员工没有待办时不推理。等待部署、外部回复或时间条件时以事件/定时唤醒和确定性查询为主，无需不断调用模型。持续无进展、重复相同失败、截止时间到期、权限撤销、效果不明和需要用户决定时都应停止或等待；“直到完成”不允许解释为无限模型循环。

## 完成与回执

Run 结束和 Task 完成分开。只有任务声明的检查通过，Task 才进入已完成；其余按部分完成、待验证、失败或等待用户处理显示。确定性结果检查优先；模型评价须标注其判断性质，不能代替真实外部状态。

回执首先展示结果、实际变更、检查及其证据、未完成部分、消耗与剩余额度、下一步和可撤销情况。较长任务允许中间进展回执，最终回执必须引用已保存的结果，而非仅引用员工的总结。

## 落地顺序和验收

1. 收稳三类有明确结果的任务、作用范围、异常恢复和执行回执，形成 feature map 与版本化技能。
2. 员工/Team 的持久配置、归属校验、模型选择和头像，管理页面与 Arc Chat 使用同一 CRUD 和草稿确认接口；创建后不自动执行。
3. 在现有任务注册表接入共享预算、跨运行检查点和持久任务创建卡片，覆盖重启、断线、重复唤醒、截止时间与预算耗尽。
4. 多员工分工和交接复用同一根任务，覆盖并发预算竞争、权限交集、成员变更和协调成本；只有验收通过的范围才对外宣称可用。

必须覆盖：跨账户读写拒绝、草稿不能代替用户确认、重复确认不重复创建、空闲零模型调用、不可用模型不擅自替换、子工作不能增加预算、并发预留不超额、未知写入不重放、没有证据不误报完成。对外文档持续区分已交付与设计中的能力。
