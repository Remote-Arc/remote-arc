# Approved browser authentication

Dashboard → Devices → Manage individual skills → Browser authentication lets the owner approve OTP sign-in/registration and CAPTCHA interactions for a device and exact website origins. Both permissions start off. Enable Browser Runner separately, enter the target website origins (including any identity provider that hosts the OTP form), optionally name the code mailbox, and select **Approve and save**. Revoke here at any time.

The Relay reads the saved authorization for every browser call and sends it in the authenticated device policy, separate from model arguments. The Agent checks both the task scope and authentication scope. Snapshot `authentication` states whether OTP and CAPTCHA are authorized on the current site. A local `browserRunnerOneTimeCodes:false` setting and the extension's code switch can still disable OTP. Mailbox is guidance to the caller; the connected mail app independently controls account access and returns the code. Remote Arc does not acquire new mail access from this setting.

Use a fresh OTP addressed to the intended account for the intended site. Both `shared_tab_fill` and `shared_tab_act` use the same approved OTP fill path. Codes remain redacted in snapshots and are absent from browser checkpoints and audit records. Authentication steps can be repeated; a final application, payment or post retains its separate submit authorization and deduplication.

For CAPTCHA, use Browser Runner. Approved sites may expose visible embedded verification frames from hCaptcha, reCAPTCHA, Turnstile, Arkose and GeeTest. Provider exceptions apply only inside a task on an approved top-level site and never authorize top-level navigation. Other frames still require the task's explicit origins. The caller can request `include_captcha_images:true` on `browser_runner_snapshot` for up to two cropped visible challenge images and then act on snapshot refs. CAPTCHA response tokens remain private: the provider generates them; the Agent never fills or returns them. DOM-accessible controls and image tile controls can be operated; closed-shadow, canvas-only, rate-limited or otherwise unsupported challenges still need user handoff. This does not guarantee every third-party challenge can be completed.

Rollout: apply migration `0067_browser_auth_permissions.sql`, deploy the Relay/UI and update the Go Agent and Chrome extension together. New clients advertise `browser_auth_policy_v1`. The Relay rejects fill operations on older clients with `BROWSER_AUTH_UPDATE_REQUIRED` so they cannot silently ignore a revoked or absent Dashboard approval. Refresh/reconnect cached MCP tool lists after deployment.

Validation uses synthetic OTP and CAPTCHA pages only, including missing approval, wrong origin, immediate revocation, code redaction, visible challenge actions and cropped images; no real accounts or applications are submitted.
