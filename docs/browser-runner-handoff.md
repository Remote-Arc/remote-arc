# Browser Runner handoff and live view

Browser Runner uses an installed Chrome, Edge or Chromium window on the linked computer. By default the window runs out of sight. It is not a cloud browser or a truly windowless browser. True headless operation and datacenter IP addresses can cause sites to request more verification; use a computer with a display for human handoff.

After a submit or navigation, the Agent checks for visible verification, sign-in and one-time-code blockers. It notifies its owner and automatically shows the existing window only when the page needs human input and the local desktop reports the owner present. Locked, idle or unrecognized sessions use notifications only. Presence is a conservative OS signal: Windows uses the current input desktop and input within two minutes; macOS uses console ownership, lock state and input within two minutes; Linux uses the active session's lock/idle hints. No input contents are collected.

The Relay forces **Notify only** for scheduled automations and routed Arc runs, regardless of model arguments. Dashboard device settings can also select this for meetings or presentations. Policy is saved per task, so simultaneous interactive and background calls do not affect each other. Each human handoff is raised at most once, including across Agent restarts. A failed raise can retry; once presented, manual minimization and later occlusion are respected. Repeating model calls, including `start`, does not undo minimization. Open the existing task window yourself when ready.

On Windows, a temporary `HWND_TOPMOST` → `HWND_NOTOPMOST` transition with `SWP_NOACTIVATE` raises only the Runner-owned window without changing keyboard focus or leaving it permanently topmost. Confirmation checks actual native Z order and overlapping visible windows, as well as screen bounds. macOS and Linux use the browser's native bring-to-front operation; CDP does not provide an occlusion query there. Password blockers require at least eight pixels in each dimension, allowing compact 16px controls while ignoring 1px bait. Hidden, inactive CAPTCHA frames do not stop a task. OTP and CAPTCHA authentication always use this handoff. Authentication automation is disabled for public MCP and internal Relay calls, and saved approvals cannot enable it. Response tokens remain private. See [browser authentication](browser-authentication.md).

Cold startup belongs to the session: a fresh profile keeps its existing 60-second startup allowance (30 seconds for an established profile), independently of the 40-second tool-call budget. If launch is still pending after eight seconds, the call returns `state=starting` and a retry interval. Repeat the original `browser_runner_start` request, including any original `start_url`, to join the same launch. Other page actions remain unexecuted until start finishes. Pending launches count toward session/profile limits and are cancelled by close, Agent shutdown or idle collection. An actual startup failure is returned on the next start/status call.

Startup diagnostics log begin/end, elapsed milliseconds and outcome for `launch`, `pageTarget`, `dialCDP`, `setup` (including individual CDP setup commands) and `navigate`. Launch also records process creation, port-file readiness and local endpoint readiness. Timeouts retain their phase and CDP method. Logs omit URLs, page contents, browser arguments and error payloads. These timings diagnose intermittent startup stalls; a passing run alone does not establish their root cause.

Use `browser_runner_wait` with `until=user_done` to wait while the owner finishes. Other conditions are `page_change`, `text`, `url_contains`, `upload_done` and `idle`. Each call waits locally for up to 40 seconds and returns `met`, `timeout` or `needs_user`. A timeout can be followed by another wait. Waiting never authorizes or retries a submit; inspect the result and confirm the existing effect.

For managed background processes, use `process_status` with `wait_ms` and optional `until_text`, rather than repeated sleep/output calls. Values over 40000 are capped.

The live-view page is available only to the signed-in device owner. It starts a view-only JPEG stream while someone is watching, at most two frames per second, capped at 200 KB per frame. A viewport capture supplies the first frame and refreshes a static or occluded page if screencast frames stop. It leaves the browser viewport and native window unchanged; Retina images are scaled locally before forwarding. Frames pass through memory only and are not saved, logged or sent to a model. A missing heartbeat stops capture after 30 seconds. Complete verification in the task window on the computer; remote input from the live-view page is a later feature.

A task waiting for the owner or carrying an unresolved final submit cannot be closed accidentally. Deliberate abandonment requires `force=true` and a reason, recorded in the task receipt. User handoffs have a two-hour timeout with one reminder before collection. Checkpoints survive collection and Agent restarts. If a browser must be reopened after restart, `reentry_needed` lists fields and uploads that must be restored; earlier receipts are history, not proof that the reopened page still contains them.

Rollout: apply migration `0064_runner_attention.sql` before the Relay, then update the Go Agent. Old Agents continue to support their previous tools; new wait/live-view operations require an updated Agent. Video upload support is tracked in #340 and must be released before validating the MP4 flow in #342. Test only synthetic forms, including delayed visible CAPTCHA challenges; do not use real employer submissions for acceptance tests.
