# 用户体验运营工作台

管理员从「用户体验」查看用户在哪一步受阻，而不是逐条阅读技术日志。

1. 先看「优先核查」。已收款但订单未处理、权益未发完整的记录优先展示；历史异常按类型合并，最多展示四条线索，可翻组查看。
2. 打开「查看原因与下一步」，了解相关账户、发生时间和建议。可查看该用户的其他操作；需要技术协助时再展开排查信息并复制。
3. 在「用户操作」输入完整邮箱或账户编号，选择业务环节。每页展示八条操作；追踪号等高级筛选默认折叠。

付款与权益核查独立覆盖全站近期订单，不随用户、环节或活动时间筛选变化。核查只读取已有记录和支付平台状态，不发起扣款、退款或补发权益。未完成订单可能是用户离开购买页，不能当作付款失败。

## 指标口径

- 有活动的账号：筛选范围内有记录的已识别账号数。
- 出现异常的账号：发生过失败记录的已识别账号去重数，不是未恢复问题数。匿名设备请求另在线索中展示。
- 完成购买的访问：带访问标识且已核验付款与权益的访问数，不是订单数。
- 购买各步骤独立统计，无法据此直接计算按序转化率。浏览器返回付款页的信号不等于实际扣款。
- 右侧 30 天会员购买来自既有付款、会员和 Credits 记录，不代表当前有效会员总数。

支付检查随页面首次打开与手动刷新执行，没有新增后台轮询。活动与支付请求独立加载；一侧失败不会隐藏另一侧已有数据。读取失败显示未知状态，不显示为零或“全部正常”。

## 隐私与实现边界

事件表仍不存储邮箱。管理员接口在现有 host、session、当前管理员角色和 no-store 校验后，单独读取当前批次最多 100 个相关账号的邮箱；邮箱检索使用参数绑定。匿名记录不猜测用户身份。

新设备配对轮询在 HTTP 400 且明确返回 `authorization_pending` 时记为 waiting。真正的鉴权、过期或其他失败继续保留。历史 `REQUEST_FAILED` 记录无法可靠反推出原始原因，不改写为成功或等待；页面提示先核对当前连接状态。

支付通知的当前处理状态优先使用账本核查，避免把已经恢复的历史失败重复当作现存支付问题。历史事件仍可在用户操作中检索。技术事件名、状态码与追踪号保留在按需打开的详情中。
