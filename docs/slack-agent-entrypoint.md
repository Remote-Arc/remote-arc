# Slack as an Arc / Archer conversation entrance

Status: implemented for production promotion, 23 October 2026. Deployment and real provider acceptance are tracked separately in REM-42. The Slack Bot is named Remote Arc.

## What is available now

The current Slack App uses **user OAuth**. Its published tools can list authorized conversations, read/search messages and threads, send/reply/update messages and manage the supported reactions, pins, bookmarks and scheduled messages. User scopes, channel membership and workspace policy apply. See `apps/relay/src/app-slack.ts` and `app-oauth.ts`.

The separate Bot integration accepts ordinary human DMs and explicit `@Remote Arc` mentions. It verifies Slack signatures, writes an encrypted durable event journal and acknowledges before asynchronous execution. It ignores Bot/self events, edits and arbitrary channel messages. Every initiating Slack identity must explicitly sign in and link its own Remote Arc account; installing the workspace Bot never grants access to the installer's account.

Requests use the existing Arc run controller, model gateway, wallet, plan limits, device ownership and tool permissions. Trial users use Auto. Plus, Pro and any higher plan with the existing paid-model entitlement can choose a configured model in Apps → Slack → Accounts. The preference applies to new Slack requests and is rechecked by the backend. A downgrade uses Auto. Trial access expiry does not remove remaining trial Credits; using Arc after trial access ends still requires an active paid entitlement.

Conversation identity includes workspace, initiating Slack user, Arc owner, channel and thread. DM turns reuse their conversation. Results from shared-channel mentions are delivered privately, never published to the shared channel. Existing web task links expose the full execution record and any required account consent. `stop` / `cancel` stops the current conversation without inference, including after trial expiry. `unlink` / `disconnect` revokes the identity link and cancels its active Slack tasks. Uninstall and Bot-token revocation stop workspace tasks.

Delivery stores Slack message IDs. A known message can be updated safely after a retry; an uncertain first post is journaled without blindly repeating the external write. Ingress and Arc completion warm the bounded queue, and the minute cron recovers it. Events are retained for 30 days; linking codes expire after 10 minutes.

## Platform setup

1. Use the existing Remote Arc Slack application, keep user OAuth for outbound tools, and enable Public Distribution for external-workspace installs. This is separate from Slack Marketplace approval.
2. Apply the manifest generated by `apps/relay/scripts/apps-registration.ts`: writable Messages tab; Bot scopes `app_mentions:read`, `chat:write`, `im:history`, `im:write`, `users:read`; preserve the current user scopes and original OAuth callback.
3. Add the Bot callback `https://mcp.remotearc.app/api/slack/oauth/callback`. Store `APP_SLACK_SIGNING_SECRET` in GitHub Actions; the production release provisions it into the existing Relay Worker. Existing Slack client credentials and the Apps vault key are retained.
4. After deployment, verify the Events API URL `https://mcp.remotearc.app/api/slack/events` and subscribe to `message.im`, `app_mention`, `app_uninstalled`, `tokens_revoked`. Reinstall via the Remote Arc Bot button to grant Bot scopes; an old user OAuth connection alone does not install the Bot.
5. Open Remote Arc in Slack Apps, send a message and complete the explicit account-link confirmation. The original request continues automatically.

`pnpm --filter @remotearc/relay test:slack` exercises signed ingress → all SQL migrations → explicit account linking → real Arc admission/budget/tool execution → private replies with isolated provider fixtures. Browser tests cover the account controls, model state and recoverable provider errors on desktop/mobile. Scripted tests do not claim a real external-workspace installation or live Slack delivery.

## Execution boundaries

1. Install a Bot with the narrowly required scopes and explicit workspace consent. Keep Bot installation separate from the current user's Slack tool authorization.
2. Accept direct messages and explicit channel mentions. Verify the raw request's Slack signature and timestamp before parsing or acknowledging work. Deduplicate events by installation and event ID, ignore Bot/self events and message edits, and acknowledge within Slack's delivery window before asynchronous processing.
3. Bind the **actual initiating Slack user** to an authenticated Arc account, not the installer's account or an email match. A workspace installation alone cannot spend an owner's Credits or access their Gmail, devices or memories. Unlinked users receive a sign-in/linking action with no task dispatch.
4. Map workspace + channel + thread + principal to a persistent Arc conversation. Start with private DMs and explicit mentions, maintaining per-user isolation even inside a shared thread. Channel-visible output must not disclose personal App/device data without an explicit sharing decision.
5. Feed the user's request through the existing Arc run controller, current access/budget gates and tool dispatcher. Reply in the same Slack thread with the outcome and evidence; do not build a second agent engine for Slack.
6. Persist outgoing reply identity and uncertain delivery. Retry handling must not duplicate an external write or recursively trigger the Bot. Support stop, revoked membership, uninstall/revocation and linking removal. Never use channel text as administrator authority.

## Acceptance before enablement

- Real workspace installation and event verification, including signed invalid/stale/retried events.
- Two users in one workspace cannot cross accounts, spend another user's allowance or expose another conversation's memory.
- Follow-up messages reuse the correct conversation and discovered context; a thread does not silently join unrelated principals.
- An actual App/device task returns an inspectable result; permissions/limits/missing capabilities produce a clear blocker.
- Partial/unknown writes survive restart without replay; bot messages, retries and edits cannot start loops.
- Public channel output observes its audience boundary; personal results default to a private conversation.

This gives users one teammate in Slack backed by the same persistent execution infrastructure. A group of autonomous developer/design teammates is a later feature requiring separate role, resource, budget and coordination boundaries.
